# Usability review — October 27, 2026

Independent design and detector/browser assessments. Target: web/shell.js and its bill, collection, home and research flows. Expert inspection, not a measured user study. Overall: 20/40.

The visual identity is coherent and deliberate: warm paper, restrained olive, readable typography and useful source disclosures. The largest problem is conceptual complexity. The application exposes its research architecture before helping a person find, follow and understand a bill.

## Priority issues

1. **P1: Home is an operations log.** Both browser assessments found 17 refresh failed/recovered events before watched bills. At1280x720, watched bills were below the first viewport. Show a bill search, watched bills and substantive legislative changes first. Collapse source service health into one current notice; retain full history in Activity. Suggested follow-up: impeccable distill.
2. **P1: Bills navigation opens administration.** Bills & collections leads with Create audited sample and All source records, while creating a collection expects machine-style bill identifiers and does not import them. Lead with title/number/issue search, clear local-data scope, Follow, and saved lists. Keep the visual map as a Bills view alongside List, not a separate conceptual destination. Suggested follow-up: impeccable shape.
3. **P1: Research requires too many concepts.** Campaign, session, experiment, sample and worker settings divide one intention across screens. Live campaign displayed Active with zero completed and eight blocked experiments plus repeated blocked notifications. Provide a guided question → scope → readiness → run flow, one Start/Pause control, and actionable blockers. Preserve advanced budgets, frozen protocols, audit gates and full reports. Suggested follow-up: impeccable onboard.
4. **P2: Bill and result pages need plain-language hierarchy.** Examples include Passed origin, raw ISO timestamps, prior families and Brier metrics. Lead with exact legislative status, a brief sourced explanation, latest change and next action. Use answer → evidence → full research record disclosures. Keep unavailable distinct from0%; completed run distinct from improved model. Mobile390px had no horizontal overflow but the summary began around y670. Suggested follow-up: impeccable clarify.
5. **P2: Navigation and accessibility lose context.** Source collection returns to all sources, not the originating collection. Sidebar lacks aria-current; bill detail lacks a main landmark/skip link; repeated Review evidence controls have ambiguous accessible names. Preserve back/list/filter/cutoff state, add semantic navigation and specific accessible names. Deduplicate identical inspector timeline events while retaining all source records. Suggested follow-up: impeccable harden.

## Proposed simple structure

Home | Bills | Research | Chat. Preserve the requested chat experience, with contextual Ask about this bill actions. Home contains changes and followed bills. Bills contains Search, List/Map and saved lists. Research contains guided experiments, unified results and advanced evidence/data tools. Activity and Connections are secondary utilities.

Everyday path: find bill → understand status and sourced summary → Follow → see meaningful updates. Research path: describe question → review suggested scope and evidence readiness → run → see plain-language result → inspect methodology if needed.

## Strengths

Clear distinction between unavailable estimates and zero probability; official summaries/source links; restrained consistent styling; progressive disclosures; preserved results, preflight gates and retained form edits.

## Persona concerns

First-time user: cannot discover a bill directly from Bills & collections without choosing an administrative concept. Busy lobbyist: source refresh noise displaces watched legislation and actionable change. Researcher: fragmented reports and repeated blockers make it difficult to identify the latest useful result. Screen-reader user: repeated generic button names and missing active navigation semantics impair orientation.

## Evidence and limits

CLI detector returned zero findings across shell.js, consumer-flow.js and research-flow.js. Browser evidence still found the issues above. Desktop and one390x844 bill page were inspected; mobile had no page-level horizontal overflow. No console warnings/errors observed. Error recovery was code-reviewed, not deliberately fault-injected. No live diagnostic overlay: browser evaluation is read-only. No application data or code was changed. Tooling could not complete a large source-ledger accessibility snapshot; that does not establish a visual app failure.

## Questions for implementation

Priority: simplify daily bill tracking first (recommended), or experiment monitoring first? Scope: redesign the navigation and task flows (recommended), or retain the layout and simplify labels/disclosures only?
